## 1. Why this exists, and why it is not a sync

The checklist app holds no Smartsheet credential. Today the calendar is fed by
`scripts/sync-contractor-schedule-from-smartsheet.ts`, which reads a JSON snapshot captured by hand
through an MCP session. That is manual and one-way.

Both repos already recorded the same intended end state, independently:

- `scripts/sync-contractor-schedule-from-smartsheet.ts:7` — *"later the middleware that writes the
  sheet will post to both, and this goes away."*
- `prisma/schema.prisma:225` — `ContractorNoteSource.SYSTEM` exists as *"the seam for … a post from
  Kyle's separate contractor-update project — that ingest endpoint is not built."*
- `TODO.md` §Q36 — recommendation on record: **wait for the middleware; do not automate the sync.**

So this contract builds that middleware fan-out. The Azure Function writes Smartsheet, then posts the
same resolved facts to the app. **The snapshot sync's update path is then deleted, not kept as a
fallback** — two paths writing status into the same field is how the two surfaces start disagreeing
about the same job. Its `create` path survives as the weekly plan loader; see **§10.6**, which is a
required deliverable, not a cleanup.

**Parallel, not derived.** The app receives the pipeline's own resolved facts. It does not receive
"what Smartsheet now says". If Smartsheet is down, the app still gets the update.

## 2. Direction and ownership

| | |
|---|---|
| Direction | pipeline → app, **one way only** |
| The app must never | write back to Smartsheet, create `ContractorJob` rows from an update, reopen a terminal job |
| The pipeline must never | read the app, or depend on the app to complete a Smartsheet write |
| Source of truth for the plan | Gerardo's workbook → Smartsheet (unchanged) |
| Source of truth for what a crew reported | this fan-out |

## 3. Insertion point (pipeline side)

In `azure/function_app.py`, the voice path currently runs:

```
update_row  →  attach_to_row  →  add_row_comment
```

The app post goes **third, before the comment**:

```
update_row  →  attach_to_row  →  POST /api/webhooks/contractor-update  →  add_row_comment
```

**This ordering is load-bearing.** `update_row` is a plain overwrite and `attach_to_row` is
idempotent (P40), so both survive a re-run at no cost. `add_row_comment` is **not** idempotent. With
the post placed before the comment, a failed post can **raise** and let the queue re-run the whole
message — the only backoff long enough to outlast a wobble — without ever double-posting a Smartsheet
comment. Placing it after the comment would force best-effort-and-silent, which is the failure shape
that cost this project 9 photos on 08/04 and 4 whole updates to the P42 duration gate.

Same rule on the image path (`_handle_image`) and the flag path (`_flag`).

**Consequence, stated plainly:** an app outage now delays the Smartsheet comment by one queue retry.
That is the intended trade. If it proves too expensive, the fix is a separate queue for the fan-out,
**not** a silent best-effort call.

## 4. Transport and auth

| | |
|---|---|
| Endpoint | `POST /api/webhooks/contractor-update` |
| Content type | `application/json; charset=utf-8` |
| Auth | HMAC-SHA256 over the **raw request body**, header `x-webhook-signature` |
| App-side helper | reuse `lib/network/hmac.ts` — already in production for the UniFi/Aruba receivers |
| Secret | Key Vault `checklist-app-webhook-secret` (pipeline) · Vercel env `CONTRACTOR_UPDATE_SECRET` (app) |
| Fail-closed | in production an unset secret rejects every request, matching `app/api/cron/generate-checklists/route.ts` |
| Timeout | pipeline waits 10 s, then raises |

**Capture before trust.** The app persists the raw body to `RawWebhookPayload` **before** parsing or
mapping, with a new `source` value, exactly as the UniFi receiver does. A mapping failure then never
loses a crew update; it leaves it recoverable. This matters more here than for UniFi — a lost webhook
here is a contractor's report of a day's work.

## 5. Idempotency

`messageSid` is the key. Twilio retries any webhook that does not return 2xx, and the queue re-runs
whole messages, so the app **will** see duplicates.

- A repeat `messageSid` returns **`200 {"ok": true, "duplicate": true}`** and writes nothing.
- Never 409. A 4xx reads as retryable to some callers and this is not an error.
- Enforce it with a unique constraint, not a `findFirst` check — two queue workers can overlap
  (`visibilityTimeout` is 6 min against a 5-min `functionTimeout`).

| Field | Source in `function_app.py` |
|---|---|

| `channel` | `"voice"` \| `"image"` \| `"text"` |
| `outcome` | `"written"` \| `"flagged"` — mirrors the blob tag |

| `contractorPhone` | `normalize_phone(form["From"])`, E.164 |
| `contractorName` | canonical roster name (`contractor`) |
| `scheduledPropertyId` | `sched["property"]` mapped to the Stayable code |
| `scheduledTask`, `priorStatus` | `sched["task"]`, `sched["status"]` |
| `actualProperty` | `result["actual_property"]` — non-null means off-plan / property mismatch |
| `roomOrArea` | `result["room_or_area"]` — free text: `"125"`, `"lobby"`, `"roof"` |

| `summary` | `result["summary"]` — the same line written to `Latest WhatsApp Update` |
| `matchesScheduledTask`, `confidence`, `notesForGm` | `result[...]` |
| `detectedLanguage`, `transcriptOriginal`, `transcriptEnglish` | `result[...]`, `text` |

| `mediaBlobUrls` | `media_store` blob names, container `media` |
| `smartsheetRowId` | `sched["row_id"]` — **audit reference only, see §7** |

`status` is sent as the **raw Smartsheet vocabulary** (`Pending` · `In Progress` · `Completed` ·
`Delayed` · `Off`), not pre-mapped. Mapping is the app's decision and belongs on the app's side of
the boundary, next to its enum.

**Not sent:** raw audio or image bytes. The app receives blob URLs. Photo capture in that app is a
geofence-verified R2 pipeline (ADR-016) and crew WhatsApp photos are not that; conflating them would
put unverified images into a verified store.

## 7. Job resolution (app side) — key on `(workDate, contractorPhone)`

**Resolve `(scheduledFor, contractor)` → `ContractorJob`. Do not key on `smartsheetRowId`.**

Three reasons:

1. **The weekly rollover destroys every `rowId`.** `rollover_schedule.py` clears all rows and loads
   the new week, so row IDs change every Monday. The existing sync's `auditLog.after.sourceRowId` map
   therefore goes stale weekly by design.
2. `(date, contractor)` is this pipeline's proven unique key — verified zero collisions across all
   populated rows, and it is what the pipeline itself resolves on every run.
3. It makes the app path genuinely independent of Smartsheet, which is the point of "parallel".

Store `smartsheetRowId` in `auditLog` for traceability. Never look a job up by it.

**Contractor identity is the phone number.** `Contractor.phone` / `.whatsapp` already exist. Match on
phone first, name second. Name-only matching is unsafe here: the schedule carries documented variants
(`Joycer A. Parra Munoz` vs `Joycer Antonio Parra Munoz`, `Ronal S.` vs `Ronal Stevent`), and the
current sync's `findFirst({ where: { name } })` will miss them.

### What the app writes

| Case | Action |
|---|---|
| Job resolved | append `ContractorJobNote` (`source: SYSTEM`, `authorLabel: "WhatsApp update"`) — **always** |
| Job resolved, `status` present, job not terminal | set status per §8 |
| Job resolved, job is `DONE`/`CANCELLED` | **leave it closed.** Append the note, record the conflict. ADR-030 invariant, and it matches this pipeline's own "never downgrade `Completed`" |
| `roomOrArea` present, job `roomLabel` empty | may set `roomLabel` (free text by design) |
| **No job resolved** | `ContractorDailyNote` (`forDate: workDate`, `propertyId` if known, else null) |
| `outcome: "flagged"` | `ContractorDailyNote`, never a status change |

**Never create a `ContractorJob` from an update.** The pipeline's standing non-negotiable is *never
create rows* — scheduling is Gerardo's job. `ContractorDailyNote` is the app's native equivalent of
the Smartsheet flag row: append-only, no unique constraint on `(propertyId, forDate)`, `propertyId`
nullable. It is the correct destination and needs no schema change.

### ✅ DECIDED 08/12/26 (Kyle): unmapped or mismatched location anchors to the assigned job

**The note always lands on the contractor's assigned job, at the job's own property. `actualProperty`
goes in the note text and never moves the job.** This is the same rule the pipeline already applies to
Smartsheet — *property mismatch → leave the Property column alone, name the actual property in the
comment* — so both surfaces now say the same thing, and the existing sync's rule 3 (a property change
is reported, not applied) is preserved rather than contradicted.

No new `Property` row is needed for this, and **`OTHERS` is deliberately not created.** Two reasons.
`Property` is a heavyweight entity in that app — it carries rooms, geofences, checklist templates,
recurring rules, network devices and a Teams channel — so a row that is not a property appears in
every property picker across features that have nothing to do with contractors. And an `OTHERS`
bucket is lossy in one direction only: once unrelated locations are aggregated into it they cannot be
separated again.

That covers the case where a job exists. Two cases it does **not** cover, kept separate on purpose
because they are different failures:

| Case | Rule |
|---|---|
| Contractor has an assigned job; reports work elsewhere (off-plan) | note on the assigned job · `actualProperty` in the note · status `Delayed` → `DELAYED` |
| Contractor has **no** job that day | `ContractorDailyNote`, `propertyId: null` if the reported location is unmapped. No job invented |
| **Gerardo schedules a row at a location the app has no `Property` for** (the `Boca Condo` case) | **not solvable here** — see below |

**The `Boca Condo` case is a plan problem, not an update problem.** There is no assigned job to anchor
to, because the job cannot be created without a property. It was 30 of 65 rows on the 08/03 week and
0 rows on 08/10, so it is latent today and v1 is not blocked by it. When it returns it belongs to the
plan fan-out (§9.4), and the choice there is a **named `Boca Condo` property row**, not `OTHERS` —
Boca Condo is a specific place, and naming it keeps the calendar honest. Palm Beach County if anything
legal touches it. Until then, an unmapped property code must **report loudly and land in
`ContractorDailyNote`** — never throw, never silently skip.

## 8. Status mapping — and the `Delayed` problem

Current mapping in the sync script:

| Smartsheet | App |
|---|---|
| `Pending` | `PLANNED` |
| `In Progress` | `IN_PROGRESS` |
| `Completed` | `DONE` |
| **`Delayed`** | **`PLANNED`** ← the problem |
| `Off` | `CANCELLED` |

**`Delayed` and `Pending` are indistinguishable in the app.** `Delayed` is what this pipeline emits
for *all* off-plan work — a crew member who spent the day on something other than the scheduled task.
That is the single most valuable thing the pipeline produces, and on the calendar it would render
identically to a task nobody has touched.

### ✅ DECIDED 08/12/26 (Kyle): add `DELAYED` to `ContractorJobStatus`

`Delayed` maps to `DELAYED`. Additive enum value, additive migration.

Three things it touches, and the third is a break risk:

1. The calendar needs a status colour for it (`/maintenance/schedule`), and any status filter or
   count that enumerates the enum.
2. `DELAYED` is **not terminal**. It behaves like `PLANNED` for the ADR-030 immutability invariant —
   a delayed job can still be worked, rescheduled and completed.
3. ⚠ **`STATUS_MAP` in `scripts/sync-contractor-schedule-from-smartsheet.ts` must be updated in the
   same change.** That script stays alive until the fan-out has proved itself (§10), so for that
   overlap window both paths write the same field. If the sync still maps `Delayed → PLANNED` while
   the fan-out writes `DELAYED`, the next sync run **silently reverts** every delayed job. The
   script's own comment says the map is *"kept identical on purpose so a re-import and a sync can
   never disagree"* — that promise now has to be honoured in the other direction.

Do not map `Delayed` to `IN_PROGRESS`. Delayed means the scheduled task got no progress; that mapping
states the opposite.

## 10. Rollout and proof

Both halves are unproven until a real crew message lands in the app. Sequence:

1. App builds the receiver. Prove it against a **preview deploy** with a replayed payload — do not
   point the pipeline at production first.
2. Pipeline adds the call **behind an app setting** (`CHECKLIST_APP_URL` unset = no post). Unset means
   off, so deploying the code cannot start writing to the app on its own.
3. Point at preview, replay a known message with `proto/replay.py` (it runs the **real deployed
   pipeline**), confirm one note on one job.
4. Point at production. Watch one real crew message end to end.
5. Run for **one full week including a rollover** before step 6. The rollover is what invalidates a
   rowId-keyed design, so a week that contains one is the only week that proves §7.

### 10.6 Remove the Smartsheet → calendar update path — required 08/12/26 (Kyle)

Once step 5 passes, the existing Smartsheet-driven calendar update is **removed, not left dormant**.
Two paths writing status into the same field is how the surfaces start disagreeing, and a dormant
script is one `--apply` away from reverting a week of `DELAYED` jobs (§8).

⚠ **But `sync-contractor-schedule-from-smartsheet.ts` does two jobs, and only one of them is being
removed.**

| Path in the script | Fate |
|---|---|
| `status` · `source-status-note` · `reschedule` · `description` · `whatsapp-note` — the **update** path | **DELETE.** This is what the fan-out replaces |
| `create` — a sheet row with no linked job becomes a new `ContractorJob`. The **plan load** | **KEEP.** Nothing else loads the week |

**Delete the update path and the week stops loading if you delete the whole file.** The fan-out never
creates jobs (§7), so with no `create` path the calendar empties at the next rollover and every crew
update lands in `ContractorDailyNote` because no job exists to receive it. That is a worse board than
the one this project is replacing.

So step 6 is: **strip the script down to the `create` path**, rename it to say what it now does
(loading the plan, not syncing), and delete the update logic, the `STATUS_MAP` status writes, the
`lastSourceStatusByRowId` tracking and the note-appending. What survives is a weekly plan loader.

The `rowId → jobId` link in `auditLog` also survives, because `create` needs it to know which rows are
already loaded — but **nothing may look a job up by `rowId` for an update** (§7).

Retiring the plan loader too is §9.4, and it is explicitly out of scope for v1.

**Ambiguity to expect:** silence looks the same as success from the outside. Verify by reading the
job's notes, not by the absence of an alert.

**Known gap this does not close:** the ~35 s rollover race (`archive()` → `clear_rows()`). An update
landing in that window is lost from Smartsheet. It will now also be lost from the app, because the
fan-out fires from the same write path. Fan-out does not create a second chance; it copies the same
one.

## 11. Ownership after integration — and why sending stays here

**Decided 08/12/26 (Kyle):**

1. **The WhatsApp messaging pipeline stays in `construction_updates`.** Settled; do not re-open.
2. After the integration is proved, the checklist-app project manages **the integration and the
   calendar** — not the transport.
3. Two features are named for **later, not now**: an automatic daily reminder of each contractor's
   scheduled work, and an automatic reply when a contractor asks a question. **Both are out of scope
   for v1** and are recorded here only so the shape is known in advance.

### Why sending could not have moved anyway

The checklist app has been **deliberately stripped of every ability to message a contractor**, four
times over, and each removal is recorded:

- **ADR-028** archived Track D (dispatch + WhatsApp). Its code was *deleted, not frozen* (`94ce338`)
  and its tables dropped — `app/dispatch`, `app/j`, `lib/dispatch-message`, `lib/job-link`.
- **ADR-030** brought contractors back **"scheduling only — dispatch/WhatsApp/consent stay archived
  and do NOT return."**
- `Contractor.whatsapp` in the schema: *"Contact information only — no code path sends a message to
  this number."*
- `ContractorJobStatus`: *"Deliberately NO `DISPATCHED` value: nothing in this feature dispatches or
  messages a contractor."* And the 13 placeholder users carry `contractors.invalid` emails
  specifically *"so nothing can ever be delivered to a real person."*

Meanwhile **this** repo holds the live sender: Twilio + Meta WABA, three ONLINE senders, display name
`Stayable Contractors`, the roster allowlist in Table Storage, and a bilingual reply path (P11)
already in production.

So a literal handover — move sending into the checklist app — would have reversed four recorded
decisions and built a second WhatsApp sender next to the working one. Kyle's 08/12/26 decision keeps
it here, which is also what those four decisions already assumed.

### The split, by capability rather than by feature

| Owner | Owns |
|---|---|
| **checklist-app** | the calendar and the plan · this receiver · **deciding what should be said and to whom** |
| **this pipeline** | the WhatsApp transport — send, templates, allowlist, 24-hour window, idempotency, opt-out |

Outbound is then a **second contract with the direction reversed**: the app calls
`POST /api/notify` on the Function; the Function sends. Same HMAC pattern, same versioning. The app
never holds a Twilio credential, exactly as it never holds a Smartsheet one.

Four reasons this is the cheaper shape, not the more bureaucratic one:

1. **Business-initiated messages need an approved Meta template.** A 07:00 "here is today's work"
   reminder is business-initiated. Free-form text is only allowed inside the 24-hour customer-service
   window that the contractor's own inbound message opens. This is a WhatsApp platform rule, it is
   already tracked here as **P29**, and it shapes the reminder feature more than any code decision
   does.
2. **The roster is the allowlist.** Two senders means two allowlists, and the failure is messaging
   somebody who is not a contractor.
3. **One number the crews know.** Two systems sending from `+1 904 787 6158` with no shared
   idempotency produces duplicate reminders, and the crews cannot tell which system is talking.
4. **The silent-loss history is all in the transport layer** — the 904 webhook, the P42 gate, the
   rollover race. Keeping one transport keeps one place to look.

### On auto-replying to questions

Treat this as a different risk class from reminders, not a later increment of the same one. The
pipeline already classifies `QUESTION` and **deliberately does not write** — it alerts the GM, because
the standing rule is *default to not writing*. The outbound analogue is **default to not sending**: an
automatic answer means the machine tells a contractor what to do on a jobsite.

Recommended first version: the app drafts, a GM approves, the pipeline sends. Autonomous reply only
after the draft path has been watched in use. This is a recommendation, not a decision — it has not
been made.

### Making the handover safe for both systems

| Guardrail | |
|---|---|
| This contract is the boundary | neither side changes it unilaterally; it lives in this repo |
| Kill switch, pipeline side | `CHECKLIST_APP_URL` unset = no post. Unset is the default, so a deploy cannot start writing on its own |
| Kill switch, app side | unset secret = fail closed in production |
| No cross-repo edits | each repo's session edits **only its own repo**. An agent holding one side's context is how the other side's invariants get broken quietly |
| Wire version | `contractVersion` on every payload, so a one-sided deploy is visible (§12) |
| Sequencing | the snapshot sync is not retired until a rollover has passed (§10) |
| ⚠ Unowned | **P30 — who owns the Function app — is still open, and this is the fourth place it has surfaced** (Azure, the Logic App's `kate@` SharePoint connection, secret rotation, now the outbound sender). A handover to a *project* is not a handover to a *person*. That gap is the real risk here, not the code |

## 12. Versioning

`contractVersion` is on every payload. The app rejects an unknown major version with **200 +
`{"ok": false, "reason": "unsupported_version"}`** and a captured `RawWebhookPayload`, so a pipeline
deploy ahead of an app deploy is visible rather than silently dropped. Add fields freely; a removal
or a meaning change is a version bump.
